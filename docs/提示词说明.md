# 提示词说明（Agent 文档）

本文档记录每个 Agent 的**角色、输入、输出、规则**，方便理解和维护。所有 Agent 都遵循「角色 + Prompt + 工作流」的架构，通过 `lib/ai/provider.ts` 的 `generateText()` 统一调用模型。

## 通用提示词结构

每个 Agent 的提示词都遵循同一骨架：

```
# 角色   你是谁、唯一职责是什么
# 输入   你会收到什么材料
# 输出   严格 JSON + 每个字段的含义
# 规则   反幻觉 + 事实规则 + 格式规则
```

统一的**反幻觉原则**贯穿所有 Agent：
- 绝不编造事实。
- 无来源 / 无法确定的信息标 `UNKNOWN` 或 `[待确认]`。
- 推测只能标 `ASSUMPTION`，绝不写成事实。
- 事实账本里 `UNKNOWN/CONFLICT/ASSUMPTION` 的信息不当确定事实用。

## 1. PM（项目经理）

- **文件**：`lib/agents/pm.ts`
- **角色**：策划开始前给「项目简报」做信息体检，判断信息是否充分；不策划活动本身。
- **输入**：项目简报（11 字段，未填写的标「（未填写）」）。
- **输出**：`{summary, knownFacts[], missingInformation[], assumptions[], nextStep, requiresHumanInput}`
  - `summary`：一句话说明「已知哪些、缺哪些关键信息」。
  - `knownFacts`：简报里明确写出来的事实（只放这些）。
  - `missingInformation`：简报没写、但关键的缺失信息。
  - `assumptions`：推断出来、但简报没明说的内容（推测）。
  - `nextStep`：下一步具体动作。
  - `requiresHumanInput`：缺关键条件（日期/地点/预算/人数）时为 true。
- **规则**：绝不编造；无法确定=缺失；推测只能进 assumptions；缺关键条件必须要求用户补充。

## 2. Strategist（策划师）

- **文件**：`lib/agents/strategist.ts`
- **角色**：根据简报/研究/事实，设计三个方向明显不同的方案，供用户挑选；不是最终决策者。
- **输入**：项目简报、研究资料库、事实账本。
- **输出**：`{concepts: [A, B, C]}`，每个方案 16 字段：`name/theme/positioning/goals/targetAudience/highlights/flow/culturalElements/interaction/promotion/budgetRange/staffing/venue/risks/pros/cons`。
- **方向差异**：A 文化传播型（讲座/展览）、B 学生参与型（工作坊/体验）、C 大型传播型（游园会/晚会）——必须是**活动形式的实质差异**，不能只是措辞不同。
- **规则**：具体事实必须来自事实账本；账本没有的标 `[ASSUMPTION]`；预算区间要贴合简报总预算。

## 3. Critic（评审）

- **文件**：`lib/agents/critic.ts`
- **角色**：给三个方案「找问题」，不重写方案，也不替用户做决定。
- **输入**：三个方案、项目简报、研究资料库、事实账本。
- **输出**：`{scores{8维}, strengths[], weaknesses[], risks[], criticalIssues[], recommendation, recommendedConcept}`
  - 8 维评分（每项 0-10 整数 + reason）：strategicFit / culturalQuality / audienceAppeal / feasibility / budget / risk / originality / communicationValue。
  - `risk` 反向计分（分数越高=风险越低）。
  - `criticalIssues`：主动找 8 类问题（不现实预算、不合理人数、文化错误、无证据事实、执行困难、时间冲突、资源不足、潜在风险）。
  - `recommendedConcept`：填 "A"/"B"/"C"（AI 建议，不代表最终决定）。
- **评分标尺**：9-10 优秀、7-8 良好、5-6 一般、3-4 较差、0-2 严重问题。
- **规则**：若方案把未验证信息当事实，必须写进 criticalIssues。

## 4. Fact Checker（事实核查）

- **文件**：`lib/agents/factChecker.ts`
- **角色**：找出方案中所有「外部事实」，判断真实性状态。
- **输入**：项目简报、三个方案、事实账本、研究资料库。
- **输出**：`{facts: [{claim, evidence, source, sourceUrl, confidence, status, reason, requiresHumanVerification}]}`
  - `status` 四选一：FACT（有来源支持）/ ASSUMPTION（假设）/ UNKNOWN（无来源）/ CONFLICT（来源矛盾）。
  - `confidence`：high / medium / low。
  - `requiresHumanVerification`：UNKNOWN/CONFLICT 的关键事实、以及需确认的 ASSUMPTION 为 true。
- **规则（核心）**：**绝不凭常识判 FACT**——没来源就是 UNKNOWN（如「礼堂」无来源 → UNKNOWN，不是 FACT）；`[ASSUMPTION]` 标注 → ASSUMPTION；来源矛盾 → CONFLICT 且写明冲突双方。

## 5. Planner（详细方案）

- **文件**：`lib/agents/planner.ts`
- **角色**：把「已选方案」展开成正式、可执行的方案，补充执行细节但不改变方向。
- **输入**：已选方案、项目简报、研究资料库、事实账本。
- **输出**：16 章节字符串：`overview/goals/theme/audience/flow/program/interactive/cultural/staffing/venue/materials/promotion/budget/risk/dayOfSchedule/evaluation`。
- **规则**：外部事实必须关联事实账本，没有的标 `[ASSUMPTION]`/`[UNKNOWN]`；预算章节总额与简报一致。

## 6. Budget（预算）

- **文件**：`lib/agents/budget.ts`
- **角色**：生成分类清晰、可复核的预算，明确每笔价格来源与可信度；不假装知道当地价格。
- **输入**：活动方案、项目简报、研究资料库、事实账本。
- **输出**：`{items[{category, item, quantity, unit, unitPrice, notes, source, confidence}], summary, costRisks[]}`
  - `category` 10 类：Venue/Decoration/Food/Printing/Equipment/Transportation/Gifts/Staff/Marketing/Miscellaneous。
  - `source` 三分类：ASSUMPTION（估算）/ USER_PROVIDED（用户提供）/ SOURCE_BASED（资料/事实账本）。
  - `quantity`/`unitPrice` 必须是数字。
- **规则**：让合计贴合简报总预算；估算价一律 ASSUMPTION + confidence=low。

## 7. Copywriter（文案）

- **文件**：`lib/agents/copywriter.ts`
- **角色**：产出 9 种不同用途、不同语气的宣传文案（正式到口语）。
- **输入**：活动方案、项目简报、事实账本、研究资料库。
- **输出**：`{formalTitle, introZh, introEn, posterHeadline, posterSubtitle, socialMedia, whatsappInvite, formalInvite, mcOpening}`（9 项，各有语气）。
- **规则**：具体事实（日期/地点/联系人/电话/费用/报名方式）必须来自简报或事实账本；缺失用 `[待确认]`；双语场合中英文都要有。

## 8. Poster（海报内容）

- **文件**：`lib/agents/poster.ts`
- **角色**：提炼做海报所需的文案与视觉要素，供 Web Design 使用。
- **输入**：活动方案、项目简报、事实账本、研究资料库。
- **输出**：`{headline, subtitle, eventDate, eventTime, venue, organizer, callToAction, contact, visualTheme, culturalElements}`（10 项）。
- **规则**：eventDate/eventTime/venue/organizer/contact 必须来自简报或事实账本；缺失用 `[待确认]`。

## 9. Web Design（网页海报设计）

- **文件**：`lib/agents/designer.ts`
- **角色**：根据方案直接生成精美的 HTML/CSS 海报，内容提取与视觉设计一次成型。
- **输入**：活动方案、项目简报、事实账本、研究资料库。
- **输出**：一个完整 HTML 文档（含 `<style>`，不含 JS、不引外部资源）。
- **设计方向**：「水墨月夜·中秋雅集」——深墨蓝 `#0d1b2a` + 鎏金 `#d4a843` + 朱砂 `#b8442f` + 月白；楷体标题 + 无衬线正文；签名元素为水墨满月 + 朱砂「中秋」印章。
- **规则**：事实缺失标 `[待确认]`；中英文都要体现；只输出 HTML 本身。

## 10. Final QA（最终质检）

- **文件**：`lib/agents/qa.ts`
- **角色**：发布前最后一道 AI 检查，逐项核对、找阻碍发布的问题；不是最终批准者。
- **输入**：整个项目（简报/研究/事实/已选方案/详细方案/预算/文案/海报）。
- **输出**：`{result, summary, findings[{check, status, detail}]}`，10 项检查。
- **结论判定**：BLOCK（冲突/预算严重不一致）> WARNING（关键事实未确认/普通文案问题）> PASS。
- **规则**：任一 BLOCK 级问题即 BLOCK；非 pass 项必须点名是哪个模块、差在哪。

---

## Agent 之间的数据流

```
ProjectBrief → PM（信息体检）
  → Strategist（三方案）→ Critic（评审）→ Fact Checker（事实分类）
  → 🧑 Human Gate 1（选方向）
  → Planner（16 章节详细方案）
  → Budget（预算）→ Copywriter（文案）→ Poster（海报内容）→ Web Design（HTML 海报）
  → Final QA（质检）
  → 🧑 Human Gate 2（最终审批）
```
