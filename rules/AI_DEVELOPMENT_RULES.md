# AI DEVELOPMENT RULES

> 面向新手的 AI Event Planning MVP —— 开发铁律。
> 本文件是项目的固定规则，所有 AI / Agent 开发必须遵守。

## 一、核心铁律（25 条）

1. 不过度工程化。
2. 不主动增加用户没有要求的功能。
3. 不重写已经能工作的模块。
4. 每次只完成一个功能。
5. 每次修改前先理解现有代码。
6. 不删除已有功能。
7. 不硬编码 API Key。
8. 不把 Secret 放进前端。
9. 不把 AI 假设当成事实。
10. 所有重要外部信息必须存在来源或明确标记 UNKNOWN。
11. 所有人类审批必须真实点击。
12. AI 不能模拟 Human Approval。
13. AI 不能自动发布外部信息。
14. AI 不能自动付款。
15. AI 不能自动发送正式邮件。
16. 所有 AI 生成内容都必须允许用户修改。
17. 所有重要数据必须可追踪。
18. 所有决策必须保存。
19. 所有 AI 结果应该有版本。
20. 如果不确定，不要编造，明确告诉用户 UNKNOWN。
21. 优先可运行性，而不是代码数量。
22. 优先简单，而不是复杂。
23. 每完成一个阶段必须可以独立运行和测试。
24. 不要一次性生成整个项目。
25. 如果发现架构问题，先说明，再修改。

## 二、架构师补充规则（本项目落地）

### A. 架构与分层

26. 所有模型调用必须统一走 `lib/ai/provider.ts` 的 `generateText()`（文本）或 `generateImage()`（文生图）；业务代码和 Agent 不得直接 fetch 模型端点，也不得写死 Provider。
27. Agent 一律用「角色 + Prompt + 工作流」实现，不实现自主多智能体互相通信。
28. 业务代码中不得出现 DeepSeek / OpenAI / Claude 等具体 Provider 的专属逻辑或字段；文本模型换模型只改 `EP_AI_BASE_URL` / `EP_AI_MODEL`，文生图换模型只改 `IMAGE_API_*` 配置。

### B. 事实与真相

29. 事实状态机固定为：unverified → ai_checked → human_verified / rejected。AI 不得自行把任何事实标成 human_verified。
30. 关键字段（场地、日期、预算、联系人、审批、安全合规）必须能追溯到 Fact Ledger 的来源，否则一律标 UNKNOWN 或 ASSUMPTION。
31. 判定 CONFLICT 时，必须保留冲突双方各自的原文，不能只给结论。

### C. 数据与持久化

32. 每个 Agent 的输出必须解析成结构化数据并落库，不能只停留在聊天文本里。
33. 每个 AI 结果都带时间戳；重新生成时保留历史或明确版本号。
34. Human Gate 的每个决定（选择、批准、驳回）都必须落库，并成为后续步骤的输入。

### D. 工程实践

35. 每次 Agent 调用都要显式设置 max_tokens 和 timeout；本项目用的推理模型（deepseek-v4-pro）至少要给 8000+ token，复杂任务给 12000–20000。
36. 模型输出的 JSON 必须做防御性解析：解析失败给出可理解的错误提示，不能让页面崩溃。
37. 提示词用中文书写并明确输出 JSON 格式；解析时对字段做类型与取值范围校验。
38. 引入新依赖前先判断是否 MVP 必需；能用原生 fetch / 标准库实现的，不引入新包。
